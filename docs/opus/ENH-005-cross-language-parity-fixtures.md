# ENH-005 — Shared Python↔TypeScript parity fixtures

> **Impact**: medium · **Effort**: small · **Status**: shipped in 0.15.0
> Source: Opus deep audit, 2026-07-28, commit `8e5d549`

## Goal

Turn two hand-maintained cross-language contracts into machine-checked ones, so that divergence fails
CI instead of surfacing as a production bug. The contracts are vault-path resolution and the
`graph.json` schema.

## Current state

The par-mem graph makes the stakes concrete. The two highest-centrality articulation points in the
codebase, one per language, implement the *same contract*:

| Symbol | File | In-degree | Articulation point |
|---|---|:---:|:---:|
| `resolve_vault` | `skills/parsidion/scripts/vault_path.py:285` | **62** | yes |
| `resolveVault` | `visualizer/lib/vaultResolver.ts:166` | **25** | yes |

Both carry source comments stating they must stay in sync — `vault_path.py:291-292` and
`vaultResolver.ts:6`. The only parity test that exists, `tests/test_vault_resolver_parity.py`, covers
`VAULT_FORBIDDEN_PREFIXES` and nothing else. **Resolution precedence is unverified**, which matters
because precedence is where the two most plausibly drift: the Python side documents
explicit flag → `cwd/.claude/vault` → `CLAUDE_VAULT` → default (`vault_path.py:296-300`), and nothing
mechanically confirms the TypeScript side agrees.

The same shape recurs for the graph schema. `build_graph.py:376-398` writes it and
`visualizer/lib/graph.ts:1-30` declares it; the audit verified they currently match field-for-field
including the conditional `parmem_body_links`, but agreement is maintained purely by hand. ENH-001 and
ENH-002 both add `meta` fields, which is exactly the kind of change that breaks such a pairing quietly.

This project already knows the pattern is dangerous — it has three `findNote` copies that diverged, and
two `findParsidionScript` implementations where one silently ignores an environment variable the other
honours. Cross-language duplication is the same failure mode with no compiler to catch it.

## Design

Emit fixtures from the Python side (which is authoritative for both contracts), commit them, and have
both test suites read them. Neither language owns the test data; both consume it.

```
tests/fixtures/parity/
  vault-resolution.json     # ordered test vectors for resolve_vault / resolveVault
  graph-schema.json         # JSON Schema for graph.json
```

## Implementation

### Step 1 — Define the vault-resolution vector format

Each vector is a fully-specified environment plus an expected outcome. Paths are expressed as tokens
so the two runtimes can substitute their own temp directories.

```json
{
  "$comment": "Generated by scripts/gen_parity_fixtures.py. Do not hand-edit.",
  "version": 1,
  "vectors": [
    {
      "name": "explicit argument wins over everything",
      "explicit": "{TMP}/explicit-vault",
      "cwd_marker": "{TMP}/proj/.claude/vault",
      "env_CLAUDE_VAULT": "{TMP}/env-vault",
      "expect": "{TMP}/explicit-vault"
    },
    {
      "name": "cwd marker beats env var",
      "explicit": null,
      "cwd_marker": "{TMP}/proj/.claude/vault",
      "env_CLAUDE_VAULT": "{TMP}/env-vault",
      "expect": "{TMP}/proj-vault"
    },
    {
      "name": "env var used when no marker",
      "explicit": null,
      "cwd_marker": null,
      "env_CLAUDE_VAULT": "{TMP}/env-vault",
      "expect": "{TMP}/env-vault"
    },
    {
      "name": "traversal in explicit argument is rejected",
      "explicit": "{TMP}/vault/../../etc",
      "expect_error": "forbidden"
    },
    {
      "name": "sibling directory does not satisfy containment",
      "explicit": "{TMP}/ParsidionVault-evil",
      "expect_error": "forbidden"
    }
  ]
}
```

Cover at minimum: full precedence order (all four channels, and each pair-wise override), every entry
in `VAULT_FORBIDDEN_PREFIXES`, `..` traversal, a symlink escaping the vault, the sibling-directory case
that `startsWith(root + path.sep)` exists to reject, an unknown vault name against the `resolveVault`
allowlist, and the not-yet-created-file case that `realpathAllowingMissing` handles.

### Step 2 — Generator script

`scripts/gen_parity_fixtures.py`, stdlib-only:

- **Vault resolution** — the vectors are hand-authored (they encode intent, not derived data), so this
  script's job is to validate them: every vector must have either `expect` or `expect_error`, names
  must be unique, and `version` must match a module constant. Fail loudly on malformed input.
- **Graph schema** — derive from `build_graph.py`. Rather than hand-writing a schema that will drift,
  build a representative graph from a small synthetic vault and infer the schema from it, then merge in
  explicit type declarations for fields that could be `null`. Include `meta.schema_version`,
  `meta.min_semantic_threshold`, `meta.max_neighbors` (ENH-001), `meta.generated`,
  `meta.parmem_body_links`, and the node/edge shapes.

Add a `make parity-fixtures` target and wire it into CI as a **check**, not a regeneration: CI runs the
generator to a temp path and diffs against the committed files, failing if they differ. Otherwise the
fixtures silently regenerate to match whatever the code now does, which defeats the purpose.

### Step 3 — Python consumer

Rewrite `tests/test_vault_resolver_parity.py` to load the fixture and parametrize over it:

```python
VECTORS = json.loads((FIXTURES / "vault-resolution.json").read_text())["vectors"]

@pytest.mark.parametrize("vec", VECTORS, ids=lambda v: v["name"])
def test_resolve_vault_matches_fixture(vec, tmp_path):
    env = _materialize(vec, tmp_path)   # create dirs/markers, set env
    if "expect_error" in vec:
        with pytest.raises(vault_path.VaultConfigError):
            vault_path.resolve_vault(**env)
    else:
        assert vault_path.resolve_vault(**env) == Path(_subst(vec["expect"], tmp_path))
```

Keep the existing `VAULT_FORBIDDEN_PREFIXES` assertion — it is still valid, now as one vector family
among several.

### Step 4 — TypeScript consumer

New `visualizer/lib/vaultResolver.parity.test.ts` reading the **same** JSON file via a relative path
(`../../tests/fixtures/parity/vault-resolution.json`), materializing each vector into a temp dir, and
asserting `resolveVault` agrees. Use `bun`'s built-in test runner and `node:fs`/`node:os` for temp dirs.

If a vector is genuinely inapplicable to the TypeScript side (for example, the visualizer may have no
concept of `cwd/.claude/vault`), do **not** silently skip it — add an explicit
`"applies_to": ["python"]` field to that vector and assert in both suites that every vector is either
executed or explicitly excluded. A silently-skipped vector is worse than no vector.

### Step 5 — Graph schema validation

- **Python side**: in `tests/test_build_graph_parmem.py`, build a graph and validate it against
  `graph-schema.json`. Use a small stdlib validator or add `jsonschema` to the `eval` extra — do not add
  a required runtime dependency, since `build_graph.py` is a PEP 723 script with only `numpy`.
- **TypeScript side**: add a compile-time check that `visualizer/lib/graph.ts`'s `GraphData` interface
  covers the schema's required fields. The pragmatic version is a test that loads the schema, builds an
  object satisfying it, and assigns it to a `GraphData`-typed variable — a type error then fails
  `bunx tsc --noEmit`.

### Step 6 — Wire into CI

Add to the `visualizer` job created by audit item ARC-007, and to the Python job:

```yaml
- run: make parity-fixtures-check   # regenerate to temp, diff against committed
```

## Verification

```bash
make parity-fixtures                     # regenerate
git diff --exit-code tests/fixtures/     # must be clean if nothing changed

uv run pytest tests/test_vault_resolver_parity.py -v
cd visualizer && bun test vaultResolver.parity
make test-graph
make checkall

# The real proof: deliberately break parity and confirm CI catches it.
# Temporarily reorder the precedence branches in vaultResolver.ts, run the TS
# parity test, confirm it FAILS, then revert.
```

That last step is not optional. A parity test that has never been observed to fail is not known to be
testing anything.

## Rollback

Purely additive — new fixtures, new tests, one rewritten test file. Reverting means deleting the new
files and restoring the previous `test_vault_resolver_parity.py` from git. No production code changes,
so there is no runtime risk at all.

## Risks

- **Fixture rot.** Mitigated by the CI diff check in Step 2: the fixtures cannot drift from the
  generator without failing the build.
- **Over-fitting the schema.** Inferring a JSON Schema from one sample can encode accidental specifics
  (an enum inferred from the three note types present in a fixture vault, for instance). Review the
  generated schema by hand once and add explicit relaxations where the inference is too tight.
- **Path semantics differ between runtimes.** macOS `/private` prefixing and Windows separators can
  make an identical logical result compare unequal. The `{TMP}` token substitution plus resolving both
  sides before comparison handles this; test on macOS at minimum, since that is the primary platform.
